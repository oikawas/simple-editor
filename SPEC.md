# Simple Editor: Specification and Design Principles

> This is a translation of [SPEC.ja.md](SPEC.ja.md). The Japanese version is authoritative.

## 1. Purpose

Provide a plain-text notes app that replaces Simplenote and runs on a home server. The goal is to keep the data in your own hands while letting several devices read and write the same notes safely.

## 2. Target environments

| Area | Target |
| --- | --- |
| Server | Docker Compose on Ubuntu (two containers, the app and Caddy; linux/amd64, linux/arm64) |
| Clients | macOS (Apple Silicon / Intel), iPhone, Android |

The client is a single web app (PWA), installed to the home screen or Dock from each platform's browser.

### 2.1 Network assumptions

- The server is assumed to be **reachable from devices on the same LAN**
- How to use it from outside the LAN (a VPN or similar) and running that is outside the scope of this app. A device that joins the LAN through a VPN is treated like any other device on the LAN
- Exposure to the internet is not intended
- Installing a PWA and running it offline require HTTPS, so connections use HTTPS even within the LAN (section 4.2)

## 3. Functional specification

### 3.1 Notes

- A note has a plain-text body. Formatting (such as rendering Markdown) is not handled
- The first non-empty line of the body (trimmed, up to 200 characters) is the **title**. A note without one is shown as "（無題）" (untitled)
- The remaining non-empty lines, joined with spaces (up to 200 characters), form the **preview** shown in the list
- The note ID is a UUID generated by the client at creation, so notes can be created offline
- The list is sorted by last update, newest first

### 3.2 Tags

- A note can have several tags
- A tag is committed by pressing Enter, comma, or space in the tag field, or when the field loses focus
- Pressing Backspace in the empty field removes the last tag
- Tags are trimmed, inner whitespace is replaced with `-`, and they are cut to 64 characters
- All tags are shown above the list; selecting one shows only notes with that tag. A note created while a tag is selected starts with that tag

### 3.3 Creation and update times

- The **creation time** is recorded by the client when the note is created. The server stores the first value it receives and never overwrites it
- The **update time** is recorded by the client 0.5 seconds after the last edit to the body or tags. Changes arriving from other devices do not update it. When it is missing, the server uses the time it stored the note
- Both are shown at the top of the editor

### 3.4 Trash

- Deleting a note moves it to the trash (sets the `deleted` flag). It can be restored from there
- Selecting "ゴミ箱" (Trash) in the list shows only deleted notes
- Permanent deletion is not offered at this point

### 3.5 Concurrent editing from several devices

- The same note can be open and edited on several devices at once. Changes reach the other devices almost immediately
- Whether edits happen at the same time or while offline, no device's changes are lost, and every device converges to the same content (automatic merging with a CRDT)
- Other devices' cursors are shown with their configured device names
- Adding and removing tags merges the same way

### 3.6 Offline

- Opened notes are stored in the device's IndexedDB and can be read and edited offline
- Notes created or edited offline are recorded as "pending" and sent automatically on reconnect. The pending state survives closing the app
- The last fetched list is kept on the device and shown while offline
- The client disconnects and reconnects following the OS network state (online / offline)

### 3.7 Full-text search

- Searches the whole body and the tags
- Whitespace-separated terms narrow the results to notes containing all of them (AND). Up to 10 terms
- Case-insensitive
- Japanese matches by substring without word segmentation; terms of one or two characters also work
- The server is queried 0.2 seconds after typing stops, and the results (up to 200) are shown in the list. Matching terms are highlighted in titles and excerpts, and each excerpt starts shortly before the match
- The search is re-run when a note is updated on another device
- While offline, the search runs on the device. Only the open note is searched by its full body; other notes are matched by title, preview, and tags (the list says so)

### 3.8 Edit history

- Every time the server stores a note, it records a snapshot of the body and tags as a "version"
- Consecutive edits are folded into one version: a store within a set time (10 minutes by default, configurable with `HISTORY_INTERVAL_MINUTES`) of the latest version's creation updates that version instead of adding one
- Nothing is recorded when the body and tags equal the latest version (for example, moving a note to the trash)
- "履歴" (History) in the editor lists the versions (save time, title, character count, newest first). Selecting one shows either a line diff against the current body (lines restoring would add / remove) or the version's full text. When the diff is too large, the full text is shown
- "この版に戻す" (Restore this version) replaces the body and tags with the version's. Restoring is an ordinary edit, so it syncs to other devices as is, and the editor's undo (Ctrl/⌘+Z) can revert the body
- Restoring always starts a new version, so the content from before the restore remains as the previous version. Text typed just before restoring (within the few seconds a store waits) may not be recorded in a version
- Viewing and restoring history requires a connection to the server
- Versions are never deleted (no retention limit)

### 3.9 Export

- **One note**: the ".txt" button in the editor saves the current note's body as a text file. It is generated on the device, so it works offline
- **All notes**: "すべて書き出し" (Export all) in the settings downloads a zip containing:
  - `<title>.txt` for each note (body only, UTF-8), with the file time set to the note's update time
  - `notes.json` with each note's file name, ID, title, tags, creation time, and update time (ISO 8601)
- File names are the title with characters not allowed in file names replaced by `_`, cut to 80 characters. An empty title becomes `untitled`; duplicates get a number such as ` (2)`
- Notes in the trash are left out (the API includes them with `?trash=1`)

### 3.10 Settings and authentication

- On first launch the settings dialog opens and asks for:
  - Server URL (defaults to the URL the app was opened from)
  - Access token (the same value as the server's `AUTH_TOKEN`)
  - Device name (shown with this device's cursor on other devices; defaults to a guess such as iPhone / iPad / Android / Mac)
- Settings are stored in the device's localStorage
- A single user is assumed, with one shared token for the whole server

## 4. Architecture

```
┌──────────── Client (PWA) ──────────────────┐
│ CodeMirror 6 ── y-codemirror.next          │
│        │                                   │
│      Y.Doc ── y-indexeddb (on-device copy)  │
│        │                                   │
│ HocuspocusProvider ─┐                      │
│ (one per note)      ├ one shared WebSocket ┼──┐
│ "__index" listener ─┘                      │  │  wss://…/sync
│ fetch ──────────────────────────────────── ┼──┤  https://…/api/*
└────────────────────────────────────────────┘  │
                                       LAN      ▼
┌──────────── Server (Docker Compose) ──────────┐
│ Caddy (:443 HTTPS / :80 certificate download) │
│   └ issues certificates from its local CA     │
│        │ http://simple-editor:8080            │
│        ▼                                      │
│ Node.js + Hocuspocus                          │
│   ├ WebSocket: Yjs sync, authentication       │
│   ├ HTTP: REST API, serves the web client     │
│   └ store hook → SQLite (better-sqlite3)      │
│   documents / notes / notes_fts / versions    │
└───────────────────────────────────────────────┘
```

### 4.1 Server

- Node.js 22 and TypeScript. Hocuspocus accepts both WebSocket (Yjs sync) and HTTP
- Documents are stored 1 second after a change (at most 5 seconds while changes keep coming)
- Every store writes the Yjs state, the list summary, the full-text index, and the history version to SQLite, then notifies every client subscribed to `__index`
- On startup, an empty full-text index is rebuilt from the stored documents, and notes without any version get a first version from their current content (for databases created before these features existed)
- Serves the built web client. Files under `assets/`, whose names contain a hash, are cached long-term; everything else is revalidated each time. Unknown paths return `index.html`

### 4.2 HTTPS on the LAN (Caddy)

- Compose puts Caddy in front to terminate HTTPS and forward to the app. The app container publishes no host port and is reachable only through Caddy
- Certificates are issued by Caddy's built-in **local certificate authority (CA)**. No public certificate authority or domain is used
  - The root certificate (valid for about 10 years) is installed and trusted once on each device
  - Intermediate and server certificates are short-lived and renewed by Caddy automatically, with nothing to do on the devices
- Certificates cover `SERVER_IP` (the server's LAN IP address) and the optional `SERVER_NAMES` (DNS names on the LAN)
- Browsers send no TLS server name (SNI) when connecting by IP address, and Caddy inside the container cannot tell which IP was dialed, so connections without SNI get the certificate for `SERVER_IP`
- Plain HTTP (port 80) only serves the root certificate (`/ca.crt`) and redirects to HTTPS
- On-device data (settings, the cached list, unsent edits) is kept per URL. If the server's IP address (or name) changes, devices treat the app as a different one, so the IP should be fixed (for example, a DHCP reservation on the router)

### 4.3 Client

- TypeScript (no framework), built with Vite. The editor is CodeMirror 6
- Only one WebSocket is opened; the open notes and `__index` are multiplexed over it
- The list is fetched again with `GET /api/notes` when `__index` reports a change or the connection is re-established
- A service worker (Workbox) caches the app shell so it starts offline. Updates apply automatically
- At 720px wide or less, the list and the editor are shown one at a time. Supports iPhone safe areas and dark mode

## 5. Data model

### 5.1 Notes (Yjs documents)

The document name is `note:<id>`, where `<id>` is 1–64 letters, digits, or hyphens.

| Key | Type | Contents |
| --- | --- | --- |
| `getText("body")` | `Y.Text` | Body |
| `getMap("meta")` | `Y.Map` | `createdAt` (ms), `updatedAt` (ms), `deleted` (boolean), `restoredAt` (when a version was last restored, ms) |
| `getMap("tags")` | `Y.Map` | tag name → `true` |

Tags are a map rather than an array so that concurrent additions and removals on different devices merge as a set, without duplicates or lost entries.

`__index` is a special document with no content, used only to deliver change notifications (stateless messages).

### 5.2 Server (SQLite)

| Table | Contents |
| --- | --- |
| `documents(name, state)` | The Yjs state of each document (binary). The source of truth |
| `notes(id, title, preview, tags, created_at, updated_at, deleted)` | List summaries, derived from `documents` |
| `notes_fts(id, body, tags)` | Full-text index (FTS5 with the trigram tokenizer), derived from `documents` |
| `versions(id, note_id, started_at, saved_at, body, tags, restore_mark)` | History versions. `started_at` is when the version was created, `saved_at` when it was last updated. `restore_mark` is the `restoredAt` at recording time; a change in it starts a new version |

The journal mode is WAL.

### 5.3 Client

| Storage | Contents |
| --- | --- |
| IndexedDB (one per note) | The note's Yjs state |
| localStorage `simple-editor:settings` | Server URL, token, device name |
| localStorage `simple-editor:notes` | Cached list |
| localStorage `simple-editor:pending` | IDs of notes with unsent changes |

## 6. Sync flow

1. Opening a note loads it from IndexedDB first, then starts syncing with the server
2. A local edit marks the note as pending, then the change is sent
3. The server acknowledges each applied change; when no unacknowledged changes remain, the note is no longer pending
4. On reconnect, pending notes, including ones not open, are opened and sent one after another (waiting up to 15 seconds each)
5. The server notifies `__index` on every store, and each client fetches the list again (and the search results, while searching)

## 7. API

Everything except `/api/health` requires `Authorization: Bearer <AUTH_TOKEN>`. A failed authentication returns 401; methods other than GET return 405.

| Method and path | Response |
| --- | --- |
| `GET /api/health` | `{"ok": true}` |
| `GET /api/notes` | Array of note summaries (`id`, `title`, `preview`, `tags`, `createdAt`, `updatedAt`, `deleted`), newest first |
| `GET /api/search?q=<terms>` | Array of `{id, snippet}`, newest first, up to 200 |
| `GET /api/notes/<id>/versions` | The note's versions: array of `{id, savedAt, title, length}`, newest first |
| `GET /api/notes/<id>/versions/<version id>` | One version: `{id, savedAt, body, tags}` |
| `GET /api/notes/<id>.txt` | The body (`text/plain; charset=utf-8`, as an attachment) |
| `GET /api/export.zip[?trash=1]` | Zip of all notes (section 3.9) |
| WebSocket `/sync` | Yjs sync over the Hocuspocus protocol. The token is sent when connecting |

## 8. Security

- The token must be at least 16 characters, checked at startup. Comparison is constant-time over SHA-256 hashes
- WebSocket connections are refused unless the document name is `__index` or a well-formed `note:<id>`
- Static file serving refuses paths that point outside the served directory
- Traffic is encrypted with HTTPS by Caddy even within the LAN, so other machines on the same LAN cannot read the token or the notes
- Only Caddy's ports 80 and 443 are published on the host; the app's port is not. Port 80 is used only for the certificate download and the redirect to HTTPS
- Host firewall rules such as ufw do not apply to ports Docker publishes. Set `BIND_ADDRESS` to listen on the LAN interface only. Do not set up port forwarding on the router
- The local CA's private key is stored in `./caddy` on the server. Anyone holding it can forge certificates for any site that devices with the root certificate will trust, so it must not leave the server
- The root certificate is downloaded over HTTP, so that first download is unprotected. Comparing the SHA-256 fingerprint shown on the device with the value on the server before installing is recommended
- The app container starts as root, fixes the ownership of the data directory, then drops to a non-root user (`node`) to run the server
- The token is stored in plain text in the device's localStorage, relying on the device's own protection (screen lock and the like)

## 9. Design principles

- **Data at hand, in plain formats** — Everything fits on one home server in one SQLite file. Backups are a file copy, and exports are plain text anyone can read
- **Sync without conflicts** — "Last save wins" or "keep a conflicted copy" approaches lose changes or call for manual merging when several devices edit at once or offline. Using a CRDT (Yjs), every device converges to the same content whatever order the changes arrive in
- **Offline as the normal case** — Phones lose their connection all the time. Changes are saved on the device first and reliably sent to the server later
- **One codebase for every device** — A single PWA is far less to maintain than native apps for macOS, iPhone, and Android. If native apps are needed later, the same web code is to be wrapped with Tauri or Capacitor
- **Few dependencies** — No UI framework; proven building blocks (Yjs, Hocuspocus, CodeMirror, SQLite) are combined
- **Self-contained on the LAN** — Nothing, certificates included, depends on services on the internet. Reaching the LAN from outside is left to whatever the user already has (a VPN or similar)
- **Derived data can be rebuilt** — List summaries and the search index are derived from the Yjs state and can be rebuilt at any time
- **Readable history, restore as an ordinary edit** — Reconstructing past points from Yjs's internal state means disabling garbage collection and growing storage. Versions are stored as plain body and tag text, readable as is and usable for export. Restoring is an ordinary edit that overwrites with the old content, so concurrent editing, offline use, and undo all keep working
- **Built for one person** — No accounts or permissions, just one shared token. Multi-user use is future work

## 10. Limitations

- Offline full-text search covers only the open note
- Permanent deletion is not implemented
- Edit history is never deleted and keeps growing; no retention period or version limit is implemented
- A single user (one shared token) is assumed
- The local CA's root certificate has to be installed on each device
- Changing the server's IP address (or name) makes each device treat the app as a different one. Edits not yet sent at that point are lost
- Body formatting (such as rendering Markdown) is not handled
